# 代码分析引擎

分析项目代码仓库，输出结构化技术事实供业务链路、贡献映射、简历和面试模块使用。本模块只说明“项目实现了什么”，不判断“用户做了什么”。

## 输入

- 项目根目录路径
- 用户指定的分析范围（目录/文件类型/关键词/自然语言描述）
- 可选：仓库索引、`.codegraph/` 或其他静态分析结果

## 分析策略

### 信息来源

允许读取 README、项目文档、代码注释和 Git 历史辅助理解项目。代码优先，文档为辅，Git 最后用于归因与演进核验：先读当前代码形成能力判断，再用测试和文档交叉验证，最后查看提交作者、时间和变更边界。不一致时以当前代码为能力事实，以用户确认和 Git 证据共同约束个人归因。

仓库根目录存在 `.codegraph/` 时，先用 CodeGraph 定位符号和调用路径，再读取关键文件验证。不存在时使用文件搜索和语言工具链。不要为了使用索引而创建 `.codegraph/`。

### 分析深度

文件级深度——读取每个模块的核心文件（前 50-100 行），理解关键类和函数。

### 大项目自适应

- 所有规模：先在用户授权范围内完成模块、入口、测试、基础设施和业务域清单；用户授权整个仓库时才覆盖全仓，避免只分析最近提交或首个命中模块。
- 小型（<3 万行）：文件级深度，全量分析。
- 中型（3-10 万行）：模块级深度，读每个模块的入口文件，再深挖高价值候选。
- 大型（>10 万行）：先做全仓模块级覆盖，再对价值最高且分属不同类别的 2-3 条链路做关键路径深挖；报告未深挖区域。

### 失败处理

深度分析失败时：
1. 自动换分析策略重试一次（如文件级降为模块级）
2. 仍失败则降级为轻量概览模式（仅目录结构 + 文件统计 + 技术栈识别），标注「深度分析不完整」

调用关系无法确认时记录 `uncertainties`，用 `[待确认]` 标记。禁止根据命名猜测动态分派、接口实现或消息消费者关系。

## 分析维度

### 阶段一：快速概览（轻量，用于后续深度分析的基础）

#### 1. 项目概览

- 目录树结构（深度限制 3 层）
- 文件统计：总文件数、各语言文件数及占比
- 代码行数估算（排除空行和注释）
- 项目规模判断：小型（<1 万行）/ 中型（1-10 万行）/ 大型（>10 万行）

#### 2. 技术栈识别

- 编程语言及版本（从配置文件推断）
- 框架及版本（如 Spring Boot、React、Django 等）
- 数据库/存储（从依赖或配置文件识别）
- 构建工具（Gradle、Maven、npm、pip 等）
- 关键依赖库（从依赖文件提取核心依赖）

#### 3. 架构分析

- 架构模式识别：MVC / 微服务 / 事件驱动 / 分层架构 / 插件式 等
- 模块边界：识别顶层模块/包，分析模块职责
- 模块间依赖关系：分析 import/include 关系
- 调用链路：识别核心业务流程的调用路径

#### 4. 入口点识别

- Web 应用：路由定义、Controller、中间件
- CLI 工具：main 函数、命令定义
- 库/SDK：公开 API、导出接口
- 服务：RPC 定义、消息队列消费者

### 阶段二：深度分析（6 维度，按认知顺序排列）

以下 6 个维度按「做什么 → 怎么做的 → 哪里容易出问题」的认知顺序排列，每个维度控制在 3-5 行。

#### 5. 产品理解

- 一句话产品定位（项目解决了什么业务问题）
- 核心功能列表（2-3 条）
- 目标用户或使用场景

#### 6. 角色识别

- 此处识别的是**系统模块角色**，不是用户个人角色
- 列出核心模块/组件名 + 一句话职责
- 格式：`模块名`：职责描述
- 覆盖 5-8 个核心模块，按重要度排序

#### 7. 数据流

- 描述 1-2 条核心业务流程的端到端数据流转路径
- 格式：`触发条件 → 模块A（处理X）→ 模块B（处理Y）→ 模块C（输出Z）`
- 每条路径控制在 3-5 步

#### 8. 技术选型理由

- 列出 3-5 个最关键的技术选型决策
- 每个附一句话选型理由 + 一句话替代方案（如果不用这个会用什么）
- 格式：`技术X`：选型理由 → 替代方案 `技术Y`

#### 9. 巧妙模式

- 列出 3-5 个工程亮点，每个一句话描述
- 聚焦：并发处理、缓存策略、设计模式、插件机制、错误处理、安全措施
- 格式：`模式名`：一句话描述其巧妙之处

#### 9.1 候选价值节点

跨全仓记录可能形成简历要点的节点，不在本阶段声明个人归属。至少覆盖已存在的类别：

- 核心业务闭环与状态一致性；
- 架构边界、扩展机制和复杂编排；
- 并发、性能、缓存与资源控制；
- 可靠性、幂等、补偿、降级与恢复；
- 安全、权限、审计与数据保护；
- 测试策略、可观测性、发布与迁移。

每个节点记录业务对象、关键代码、技术难点、取舍、验证证据和影响边界。Git 元数据只能追加作者/时间/演进信息，不得提高节点价值分。

#### 10. 坑点

- 列出 2-3 个已知问题或技术债，每个一句话描述
- 来源：代码中的 TODO/FIXME/HACK 注释、明显的防御性代码、硬编码配置
- 格式：`问题`：一句话描述影响

分析完成后，将结果返回给主 Skill，并交给 `business-chain-extractor.md`。本模块不生成个人贡献和简历声明。

## 输出格式

### 交付方式

- `DIRECT + ANALYZE_ONLY`：在对话中交付同等结构的项目分析与业务链路摘要，不创建分析目录、文件或 manifest。
- `ARTIFACT/FULL_PIPELINE`：生成版本化项目分析文件，并通过 manifest 的 `current_artifacts` 记录当前路径。

下方内部结构适用于两种方式；文件模板只适用于 `ARTIFACT/FULL_PIPELINE`。

## 跳过规则

自动跳过以下内容：
- `node_modules/`、`vendor/`、`target/`、`build/`、`dist/`、`.git/` 等依赖和构建目录
- `*.min.js`、`*.bundle.js` 等压缩文件
- 二进制文件（`*.class`、`*.jar`、`*.exe`、`*.so`、`*.dll` 等）
- 图片/视频/音频文件
- 包含 `password`、`secret`、`token`、`key` 等敏感关键词的配置文件（跳过内容，仅记录文件名）
- 测试目录默认不做全量逐文件阅读；用户未排除测试目录时，命中候选价值节点再读取相关测试，以核对正确性、失败边界和验证范围。用户明确要求跳过测试时不得读取，改为标记“未核验测试证据”
- `.gitignore` 中标记为生成/忽略的文件

## 不要做

- 不要把模块角色写成用户角色。
- 不要读取或输出密钥、token、密码的具体值。
- 不要把 README 声明当作代码已经实现的唯一证据。
- 不要把无法确认的动态调用写成确定关系。
- 不要在本模块生成简历 Bullet 或性能提升数字。
- 不要从 commit 大小、文件数、增删行数、提交频率或文档数量推断工程价值。
- 不要因为 Git 历史容易枚举，就跳过对当前代码、调用链和测试证据的分析。
