# 来源感知的 STAR 简历生成器

从结构化 manifest 或已确认来源的单步骤材料生成一页项目经历。生成器只负责选材、组织和表达，不自行发明项目来源、角色、代码关系或数字。

## 来源前置门禁

任何生成或改写简历要点的请求都必须已有明确 `project_origin`：`OPEN_SOURCE / SELF_OWNED / INTERNSHIP / OTHER`。如果缺失，只询问“这是开源项目、个人项目还是实习项目”，然后停止；不得先给候选、示例或临时改写。

`EXISTING_RESUME` 是材料状态，不是项目来源。用户提供了现有简历也必须确认底层项目来源。不生成或改写简历的分析、拷打、学习或模拟面试任务不触发本门禁。

## 输入

- `evidence-manifest.json`
- manifest 的 `current_artifacts.project_analysis`
- manifest 的 `current_artifacts.business_chains`
- manifest 的 `current_artifacts.contribution_map`
- manifest 的 `current_artifacts.enhancement_plan`（如存在）
- `references/star-framework.md`
- `references/claim-policy.md`
- manifest 顶层 `project_origin`

`ARTIFACT/FULL_PIPELINE` 缺少 manifest 时停止生成最终简历，先回到贡献映射。`DIRECT + RESUME_ONLY` 不要求 manifest，但必须已有用户明确给出的 `project_origin`，并只使用用户当前提供的事实。来源缺失时不允许用 `DRAFT` 绕过前置门禁。

## 输出

- `DIRECT + RESUME_ONLY`：在对话中交付简历要点或完整项目经历，不创建文件或 manifest。
- `FILE_REVISION`：用户明确授权修改现有简历文件时，新建相邻的 `-vN` 修订版，不覆盖原文件，不创建 manifest。
- `ARTIFACT/FULL_PIPELINE`：新建 `{项目名}-analysis/resume.md` 或下一个 `resume-vN.md`，更新 manifest 中的 `claims[].resume_text` 与 `current_artifacts.resume`。

## 步骤 1：校验候选池

读取贡献映射中的完整候选排名。要求 N 条简历要点时，候选池应至少包含 `max(6, 2N)` 项，并来自不止一个链路或工程类别；仓库确实不足时必须有扫描范围和缺口说明。候选池只含单个提交、单一功能或同一功能的前后端/文档拆分时，停止生成最终版并返回 Phase 1-2 补扫。

先执行来源、角色、掌握度和风险准入，再读取贡献映射的 `candidate_value_score` 选择最多 10 条。不得把准入条件与价值分混算。价值分只由贡献映射中已记录的六项组成：

1. 业务/架构关键性；
2. 工程深度；
3. 方案取舍；
4. 结果/验证；
5. 岗位相关性；
6. 面试可深挖性。

Git 提交只回答归因和演进问题，不参与价值排序。以下内容不得作为核心结果：commit hash、提交次数、改动文件数、增删行数、commit 大小、ADR/设计文档数量。若静态计数确实表达业务或验证范围，必须计数业务对象，例如规则、端点、失败场景或测试用例，并说明其作用。

状态处理：

| 声明状态 | 是否进入简历 |
|---|---|
| `READY` | 进入 |
| `NEEDS_EVIDENCE` | 可进入草稿，弱化无依据结果 |
| `NEEDS_TRAINING` | 可进入草稿，必须进入拷打和学习 |
| `NEEDS_BUILD` | 完成增强任务后进入；用户坚持时以高风险草稿保留 |
| `BLOCKED` | 不进入最终版；可列在训练候选中 |

随后按 `project_origin` 应用范围准入：

| 项目来源 | 准入范围 |
|---|---|
| `OPEN_SOURCE` | 达到 `L3/L4` 且有复现、二次开发或等价实现证据时，可选择覆盖需求理解、架构设计、核心实现和验证的连续节点；只读或借用内容不准入个人全流程 |
| `SELF_OWNED` | 按真实个人/合作边界，可选择端到端流程中的多个高价值节点 |
| `INTERNSHIP` | 候选必须落在用户负责的高价值环节或同一业务目标下的一个核心闭环；跨团队全产品流程不准入 |
| `OTHER` | 默认按 `INTERNSHIP` 的聚焦范围准入；确认用户拥有并实现完整流程后才可放宽 |

## 步骤 2：生成情境

用 2-3 段说明：

1. 业务或用户问题；
2. 项目如何解决该问题；
3. 技术栈与架构定位。

只使用业务链路和项目分析中的信息。开源/他人项目迁移时，说明项目背景和复现目标，不在情境中虚构公司名称。

## 步骤 3：生成任务

任务必须说明当前用户模式和角色范围：

- 真实实习：团队目标 + 用户负责部分；
- 弱实习：实际接触内容 + 补全/复盘范围；
- 自研项目：独立或合作范围；
- 项目迁移：复现、二次开发和掌握的链路；
- 方案设计：设计、对比和验证计划范围。

任务不复述项目功能，不把整个项目职责归给用户。

实习项目的“负责部分”必须具体到重要环节或核心闭环，例如意图识别链路、知识反馈闭环、召回排序链路或故障发现-处置-复盘闭环。闭环可以包含多个连续步骤，但每一步都必须有用户角色和证据，不能借闭环之名覆盖整个产品。

## 步骤 4：生成逐条完整的 STAR 要点

每条使用 STAR 框架中的来源感知公式，并写成“主题标签 + 分隔冒号 + 正文”：中文使用 `{2-6 个汉字的主题标签}：{正文}`，英文使用 `{1-4 word label}: {body}`。标签概括并区分该条的技术决策或工程主题，不承担 STAR 要素，也不得使用 `S/T/A/R`。正文以一句紧凑表述按 `情境 -> 任务 -> 行动 -> 结果` 排列；情境与任务可以合并成一个分句，但四项不得缺失，不得只写“技术动作 + 效果”。内部保留：

```text
CLAIM-ID -> CONTRIBUTION-ID -> CHAIN-ID -> EVIDENCE-ID
```

用户可见正文不展示内部 ID，但当前简历文件末尾增加“面试准备索引”，列出简历要点序号对应的 claim ID，便于后续拷打。

### 中文优先规则

用户使用中文或未指定语言时，成品标题和叙述使用自然中文：

| 避免直接混排 | 中文默认表达 |
|---|---|
| `Bullet` | 简历要点 |
| `Action & Result` | 行动与结果 |
| `Claim` | 声明 |
| `Intent` | 意图 |
| `LLM` | 大语言模型；确需缩写时首次写“大语言模型（LLM）” |
| `Agent` | 智能体 |
| `Schema` | 数据结构约束；特指标准时保留 `JSON Schema` |
| `checkpoint` | 检查点 |

产品名、框架名、协议名、行业通用缩写和真实代码标识符按准确性保留，例如 WPS、Redis、HTTP、JSON、API、QPS、`decompose`。代码标识符首次出现时补充中文职责，例如 `decompose`（步骤拆分），不要写成“设计 decompose 将步骤……”。用户明确要求英文时，整份成品统一使用英文，不执行中文替换。

错误示例：

```text
Bullet 1 · 二段式 Intent 编译：设计 decompose 做规则拆分，未命中部分交给 LLM，最后由 finalize 校验 Schema 和 checkpoint。
```

中文成品示例：

```text
意图编译：通过 `decompose`（步骤拆分）优先将自然语言转换为确定性原子动作，未命中部分交由大语言模型补全，再由 `finalize`（最终校验）检查数据结构约束、能力注册表和检查点，提升意图生成的稳定性。
```

### 长度与数量

- 3-8 条为常用范围，最多 10 条；
- 每条正文建议不超过 100 个汉字；从列表序号或项目符号后的第一个分隔冒号开始解析正文，中文优先识别 `：`，英文识别 `:`；标签和未填写的占位符均不计入正文长度，填写占位符后重新压缩；
- 一条只讲一个核心决策或闭环，同时保留该闭环的情境、任务、行动和结果；
- 架构/业务、工程实现、质量/稳定性三类至少覆盖两类。

### 结果数字与占位符

对每条要点执行以下分支：

- `PRODUCTION/BENCHMARK/STATIC_COUNT`：写入真实指标、基线、结果和口径；
- `USER_REPORTED`：用户确认后使用，并保留口径；
- `ESTIMATED/NARRATIVE` 或缺少量化 evidence：不得填入推测值，改写为 `[待补：{指标}从 __ 变为 __，变化 __%，口径/环境 __]`；
- 用户要求可直接投递且数字仍缺失：仅当用户材料或 evidence 已确认覆盖范围、正确性验证或工程闭环时，在占位草稿之外提供稳妥版并清除全部占位符；连定性结果也未确认时，不生成“可直接投递版”，只追问一个结果事实。

带待补占位符的版本必须紧邻标记“待补数据，不可直接投递”，状态最高为 `REVIEW_REQUIRED`。稳妥版只能改写已有事实，不得补造“上线后稳定”“降低数据库压力”“获得团队认可”等结果。组件常识不能补齐 Action 或 Result：仅知道“使用 Redis”时，不得自动写缓存键、TTL、失效、回源、命中行为或数据库访问变化。指标名称必须由业务目标或验证方法支持，不能因为使用 Redis 就默认选择命中率，因为做异步处理就默认选择 QPS。

### 来源表达

不要把内部风险标签写成简历免责声明。通过动词和范围体现角色：

- `TEAM_FACT`：参与 X，负责 Y；
- `MENTOR_DIRECTED`：在既定方案下实现/验证 Y；
- `REPRODUCED`：基于 X 复现并扩展 Y；
- `DESIGNED_ONLY`：针对 X 设计并对比 Y；
- `NARRATIVE_FILL`：根据 manifest 选择最能抗追问的范围，后续强制拷打。

项目来源进一步限制整体叙事：

- `OPEN_SOURCE`：允许把已复现并实际改造的多个节点组织成完整设计与实现流程，但必须明确“基于某项目复现/改造/扩展”，不声称原创开源项目整体架构；
- `SELF_OWNED`：允许按真实角色使用“设计、实现、建立”等动词串联端到端流程；
- `INTERNSHIP`：整组要点只能覆盖用户负责的高价值环节或核心闭环，不使用“从零搭建整个系统、主导全产品架构”等越界总括；
- `OTHER`：默认沿用实习项目边界，直到所有权和实现范围得到确认。

## 步骤 5：排序与替换

唯一权威排序值为贡献映射阶段产生的 `candidate_value_score`：

```text
candidate_value_score = 业务/架构关键性 + 工程深度 + 方案取舍 + 结果/验证 + 岗位相关性 + 面试可深挖性  # 0-12
```

角色、来源、掌握度和风险先决定准入，不加到价值分中。同分时优先：结果证据更强 > 有失败处理 > 主题覆盖更互补；仍同分则保留贡献映射原排名并记录理由。

生成初稿后执行一次全量替换检查：逐个比较“最低分入选项”和“最高分未入选合格项”的 `candidate_value_score`。后者分数更高时必须替换；仅在主题重复时允许保留，并在面试准备索引中记录具体原因。角色风险在准入阶段处理，岗位相关性已计入价值分，不得在替换阶段重复加权。不得以“来自真实提交”“改动量大”或“已有静态计数”为保留理由。

同一功能默认只保留一条，合并前端交互、后端接口、数据落库和配套文档；只有它们分别包含独立的高价值决策、验证结果且能单独通过拷打时才可拆分。若最终没有足够的强/中候选，明确告诉用户当前仓库和个人归因不足，输出补强任务，不用低价值事实凑满 N 条。

## Markdown 模板

```markdown
# {项目名称}

> 本材料由 AI 辅助生成，请在投递前确认角色、数字和技术细节。

**技术栈**：{技术栈}

## 项目情境

{业务问题}

{项目作用}

{技术栈与架构}

## 负责范围

{用户角色、负责范围和目标}

## 行动与结果

1. {主题标签}：{正文}
2. {主题标签}：{正文}
3. {主题标签}：{正文}

## 面试准备索引

| 简历要点 | 声明编号 | 来源 | 风险 | 拷打状态 |
|---|---|---|---|---|
| 1 | CLAIM-001 | {source_type} | {risk} | {status} |
```

如用户明确要求纯简历版本，另生成不含“面试准备索引”的 `resume-clean.md`；内部索引仍保留在 manifest。

## HTML 输出

用户选择 HTML 时，将 Markdown 的信息层次原样转换为单页 HTML：

- 页面宽度适合 A4；
- 项目情境、负责范围、行动与结果的顺序不变；
- 不添加虚构图表或进度条；
- 打印样式隐藏面试准备索引；
- 不从外部 CDN 加载必须资源，确保离线可打开。

## 生成后自检

生成后逐条检查；失败项自动重写一次，仍失败则标记 `REVIEW_REQUIRED`：

- [ ] 项目情境是否说明业务问题、项目作用和技术栈？
- [ ] 负责范围是否与贡献映射中的角色一致？
- [ ] `project_origin` 是否已经由用户明确确认，而不是从 `EXISTING_RESUME` 或仓库类型猜测？
- [ ] 开源/个人项目的全流程表述是否只覆盖用户实际复现、设计、实现和验证的环节？
- [ ] 实习项目是否只写高价值环节或核心闭环，且没有冒领全产品/全系统流程？
- [ ] 每条简历要点是否映射到声明和业务链路？
- [ ] 每条是否使用简短、非空且互相区分的主题标签，中文用 `：`、英文用 `:` 分隔？
- [ ] 长度是否只计算第一个分隔冒号后的正文，排除标签和未填写占位符？
- [ ] 每条是否都按顺序包含情境、个人任务、技术行动和结果，而非由整组要点共同补齐？
- [ ] 是否避免使用 `S:`、`T:`、`A:`、`R:` 标签机械分段？
- [ ] 是否比较了至少 `max(6, 2N)` 个跨链路候选，或明确记录仓库不足？
- [ ] 是否只沿用 `candidate_value_score` 排序，没有在简历阶段另建评分公式？
- [ ] 是否已用更高价值且准入合格的未入选候选替换较弱要点？
- [ ] 动词是否匹配主导、实现、参与、复现或设计角色？
- [ ] 是否避免把项目整体成果自动归给用户？
- [ ] 真实数字是否有 evidence 类型、基线、结果和口径？
- [ ] 无量化证据时是否使用统一待补占位符，并明确标记不可直接投递？
- [ ] 稳妥投递版是否清除全部未填写占位符？
- [ ] 是否删除了仅表示 Git 变更规模或文档数量的伪成果数字？
- [ ] 稳妥投递版没有数字时，是否提供有证据的覆盖范围、正确性验证或工程闭环作为结果？
- [ ] 是否包含至少一条方案取舍或工程边界？
- [ ] 是否不超过 10 条且每条聚焦一个主题？
- [ ] 是否删除“深刻理解、熟练掌握、全面、完美”等主观评价？
- [ ] 高风险声明是否标记为待拷打？
- [ ] 面试准备索引是否完整？
- [ ] 中文成品是否已把可翻译的通用英文术语改为中文？
- [ ] 保留的英文是否仅限专有名词、通用缩写或真实代码标识符，并在必要时有中文解释？

## 失败模式

| 触发条件 | 一线修复 | 仍失败则 |
|---|---|---|
| 没有 READY claim | 选择最高价值内容生成增强任务 | 只输出训练草稿 |
| `project_origin` 缺失 | 只询问开源、个人或实习项目 | 用户未回答则停止，不生成草稿或示例 |
| 开源全流程缺少复现/实现证据 | 将对应节点转为增强任务 | 只保留训练材料，不写个人已完成成果 |
| 实习候选越过个人负责范围 | 收窄到重要环节或核心闭环 | 无法归因时不生成最终版 |
| 主题标签缺失、为空、过长或与相邻要点重复 | 根据正文核心技术决策重写标签，并按语言使用正确冒号 | 仍失败则标记 `REVIEW_REQUIRED`，不得称为最终版 |
| 正文计长包含标签或误切占位符内部冒号 | 从列表标记后的第一个分隔冒号重新解析，只计算正文并排除未填写占位符 | 仍无法满足长度则压缩正文，失败时标记 `REVIEW_REQUIRED` |
| 角色与代码冲突 | 回 contribution mapper | 状态 `BLOCKED` |
| 单条 STAR 缺少任一要素 | 按情境、任务、行动、结果顺序自动重写一次 | 仍缺失则标记 `REVIEW_REQUIRED`，不得称为最终版 |
| 量化结果缺少可信 evidence | 使用统一待补占位符并标记不可投递 | 只有已确认定性结果时才生成稳妥版；否则追问一个结果事实 |
| 简历要点超过一页 | 按优先级保留前 3-8 条 | 输出完整材料到话术而非简历 |
| 用户要求强行加入高风险声明 | 保留并记录 override | 强制进入拷打，状态不虚报 |
| 中文成品出现可避免的中英文混排 | 按术语表自动改写一次 | 标记 `REVIEW_REQUIRED` 并列出残留位置 |
| 候选池只来自一个提交/功能 | 回 Phase 1 补扫全仓业务域和工程类别 | 标记分析不完整，不生成最终版 |
| 更高价值合格候选未入选 | 替换最低分要点并重写；未通过准入的候选不参与比较 | 仅因与已入选项主题重复时允许去重，记录理由并标记 `REVIEW_REQUIRED` |
| 只有 Git 静态计数可写 | 回代码、测试和业务链路寻找技术决策与结果 | 输出补强任务，不用低价值计数凑数 |

## 不要做

- `ARTIFACT/FULL_PIPELINE` 不要在没有 manifest 时生成“最终版”；`DIRECT + RESUME_ONLY` 按已确认来源和用户当前事实直接交付。
- 不要在 `project_origin` 未确认时生成任何简历要点，包括标记为草稿的版本。
- 不要把 `EXISTING_RESUME` 当作项目来源。
- 不要把实习项目写成用户独立完成的全产品或全系统流程。
- 不要把开源原作者的设计写成用户原创；全流程只覆盖实际复现、改造、实现和验证的内容。
- 不要把“参与、协同”统一替换为“主导”。
- 不要凭技术组件生成性能数字。
- 不要把增强计划写成已完成结果。
- 不要为满足 STAR 格式重复堆砌同一事实；压缩情境与任务，不删除任何要素。
- 不要省略主题标签、使用空标签、复用无法区分主题的标签，或把 `S/T/A/R` 当作主题标签。
- 不要把标签计入正文长度，也不要把 `[待补：...]` 内部冒号误作标签分隔符。
- 不要让不同要点分别承担 Situation、Task、Action、Result；每条都必须独立完整。
- 不要把待补占位符当作真实结果，也不要把含占位符版本称为可直接投递。
- 不要为了交付稳妥版而虚构上线稳定、数据库压力下降、覆盖范围或用户反馈。
- 不要从 Redis、消息队列、线程池、索引等组件名称推导该项目采用的具体模式或实际结果。
- 不要绕过简历要点拷打直接标记可投递。
- 不要用 `Bullet 1`、`Action & Result`、`Claim` 等内部英文作为中文成品标题。
- 不要为了追求全中文而误译产品、框架、协议、通用缩写或代码标识符。
- 不要从 Git 历史逐 commit 生成简历，或把大 diff 当作高价值成果。
- 不要用文件数、增删行数、commit 数或 ADR 数量代替业务结果、技术难点与验证。
- 不要在存在更强且角色合格的候选时保留低价值要点。
