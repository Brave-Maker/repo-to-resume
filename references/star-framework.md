# STAR 声明框架

本模块定义经历内容的组织方式。生成简历时同时读取 `claim-policy.md`，以来源、角色、掌握度和证据约束表达。

## 四要素

| 要素 | 回答的问题 | 证据来源 |
|---|---|---|
| 情境（Situation） | 谁遇到什么问题，约束是什么 | 业务链路、用户材料 |
| 任务（Task） | 用户在团队或项目中的角色是什么 | 贡献映射 |
| 行动（Action） | 用户做了什么技术动作，为什么这样做 | 声明、代码、增强任务 |
| 结果（Result） | 改变了什么，如何验证 | 证据、测试、范围或反馈 |

## 单条 STAR 公式

每条简历要点使用一句紧凑表述，并按以下顺序组织：

```text
{情境：业务问题或约束} + {任务：个人负责范围} + {行动：技术决策与实现} + {结果：量化变化或待补占位符}
```

情境与任务可以压缩进同一分句，例如“针对活动期订单查询变慢，负责缓存改造”；但每条均必须让读者识别四个要素。不要用 `S:`、`T:`、`A:`、`R:` 标签机械切段，也不要让整组要点代替单条完整性。

整组要点的跨度由 `project_origin` 决定：开源项目在实际复现/改造后、个人项目在真实角色范围内可以覆盖端到端设计与实现；实习项目只能围绕用户负责的高价值环节或一个核心闭环展开。

## 动词选择

| 角色 | 推荐动词 | 示例 |
|---|---|---|
| 方案主导 | 设计、主导、推动、制定 | 主导幂等方案选型 |
| 独立实现 | 实现、重构、改造、建立 | 实现订单状态机 |
| 团队参与 | 参与、协同、配合、负责其中 | 参与消息链路建设，负责重试模块 |
| 复现迁移 | 复现、迁移、扩展、验证 | 复现调度链路并扩展资源组控制 |
| 方案推演 | 设计、评估、对比、规划 | 对比两种缓存一致性方案 |
| 阅读学习 | 梳理、分析、定位、总结 | 梳理请求到存储的数据流 |

不要为了“强动词”改变角色。`参与` 后接明确范围，比没有依据的 `主导` 更可用。

## 结果的六种表达

按证据优先级选择：

1. 线上业务或监控数据；
2. 本地/测试环境基准；
3. 静态可计数范围：端点、规则、模块、场景；
4. 正确性结果：通过的用例、消除的错误类型；
5. 工程闭环：监控、降级、回滚、补偿是否形成；
6. 用户或团队反馈。

没有可靠数字时，不强行写百分比。可以写“覆盖支付、取消和超时关闭 3 类路径”“验证重复消费和超时回调 2 类异常”。

## 数字与占位符规则

结果按以下顺序选择，命中后停止：

1. 有可信证据：写指标、基线、结果和口径；
2. 缺少可信量化结果：写 `[待补：{指标}从 __ 变为 __，变化 __%，口径/环境 __]`；
3. 用户要求可直接投递且仍无数字：仅当用户材料或 evidence 已确认覆盖范围、正确性验证或工程闭环时，另给不含占位符的稳妥版；连定性结果也缺失时，停止生成所谓“可投递版”，只追问一个结果事实。

占位符只属于待完善草稿，不是 evidence，不得将其解释为已完成结果。稳妥版不得加入“上线后稳定”“降低数据库压力”“获得团队认可”等未被用户材料或 evidence 确认的结果。组件常识不算项目证据：仅知道“使用 Redis”不能推出缓存键、TTL、失效、回源、命中行为或数据库访问变化；仅知道消息队列、线程池或索引时同理。一个要点只保留与行动直接相关的 1-2 个结果指标；未知指标名称时写业务目标，例如 `[待补：重复处理率从 __ 降至 __，统计周期 __]`，不要随意指定 P95、QPS 或命中率。

每个真实数字映射到 manifest evidence：

```json
{
  "id": "EVIDENCE-001",
  "type": "BENCHMARK",
  "value": "P95 420ms -> 180ms",
  "environment": "local, 4C8G, 10k records",
  "method": "wrk 60s x 3",
  "risk": "LOW"
}
```

允许 `PRODUCTION`、`BENCHMARK`、`STATIC_COUNT`、`USER_REPORTED`、`ESTIMATED`、`NARRATIVE`。后两类必须记录假设和风险，并通过数据追问。

禁止以下推导：

- 看见线程池就估算 QPS；
- 看见 Redis 就估算命中率；
- 看见消息队列就估算响应时间提升倍数；
- 看见索引就估算查询提升 10-1000 倍；
- 看见熔断就声称可用性达到 99.9%。

## 方案演进

面试材料需要解释：

```text
约束 -> 初始方案 -> 暴露的问题 -> 最终方案 -> 代价/边界
```

若代码中只能看到最终方案，不要编造历史演进。可以明确写成“复盘时对比的替代方案”，并记录来源为 `DESIGNED_ONLY/NARRATIVE_FILL`。

## 来源感知示例

### 个人事实

```text
实现订单回调幂等校验，以业务单号和事件类型构造幂等键，覆盖重复通知与超时重试场景。
```

### 团队参与

```text
参与订单状态链路建设，负责回调幂等与异常补偿模块，验证重复通知和部分失败场景。
```

### 项目迁移

```text
基于开源调度项目复现任务执行链路，扩展资源组并发控制，并在本地对比串行与并行策略。
```

### 实习核心闭环

```text
负责智能客服意图识别链路，完成规则预判、模型兜底与结果校验，并将低置信样本回流知识库，形成识别、反馈和迭代闭环。
```

### 方案推演

```text
针对消息重复消费设计唯一约束与 Redis 去重两种方案，分析一致性、存储成本和失效恢复边界。
```

## 自检

- 每条是否都能按顺序识别情境、个人任务、技术行动和结果？
- 情境与任务是否紧凑，而不是用四个标签机械分段？
- 行动是否与贡献映射中的角色一致？
- 是否能映射到 `claim_id` 和 `chain_id`？
- 技术动作是否具体到方案或实现？
- 结果是否有证据和明确口径；若没有，是否使用统一待补占位符并标记不可投递？
- 可投递版本是否已清除全部未填写占位符？
- 方案演进是否区分真实发生与复盘推演？
- 是否存在为了有力而夸大角色或数字？
- 开源/个人项目的端到端跨度是否均有实际复现、设计或实现证据？
- 实习项目是否收敛在重要环节或核心闭环，而非整个产品流程？
- 高风险声明是否进入拷打门禁？

## 不要做

- 不要省略单条中的情境、任务、行动或结果，再用其他要点补齐。
- 不要要求每条都有性能百分比；量化对象必须与行动存在因果关系。
- 不要把所有“参与、协同”替换为“主导”。
- 不要把项目能力等同于个人贡献。
- 不要把方案计划写成已上线结果。
- 不要把占位符当成证据或已验证结果。
- 不要把含未填写占位符的草稿称为可直接投递。
- 不要为满足用户的“稳妥版”要求而补造上线效果、性能改善、覆盖范围或团队反馈；没有已确认结果就停止并追问。
- 不要把组件的典型实现模式写成项目事实；“技术上通常如此”不能代替用户材料或 evidence。
