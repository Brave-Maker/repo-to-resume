# 贡献映射器

本模块把“项目实现了什么”转换为“用户可以如何描述自己”。在代码分析完成后、简历生成前执行。

## 输入

- manifest 的 `current_artifacts.project_analysis`
- manifest 的 `current_artifacts.business_chains`
- 用户口述、现有简历或工作记录
- 可选：提交记录、工单、测试报告、截图；提交记录只用于个人归因和演进核验
- `references/claim-policy.md`

## 输出

- 新建当前版本的贡献映射，并更新 `current_artifacts.contribution_map`
- 更新后的 `evidence-manifest.json`

## Step 1：确定用户模式

只选择一个主模式：

| 模式 | 判定 |
|---|---|
| `REAL_INTERNSHIP` | 有真实实习且有明确个人产出 |
| `WEAK_INTERNSHIP` | 有实习但产出零散或角色模糊 |
| `SELF_PROJECT` | 没有实习，有自己完成的项目 |
| `PROJECT_MIGRATION` | 需要从开源、团队或他人项目迁移内容 |
| `EXISTING_RESUME` | 已有简历，需要反向核验和补强 |
| `UNDERSTAND_ONLY` | 只理解代码，不生成经历 |

模式不明确时，一次只问一个最能区分模式的问题。不要让用户填写长问卷。

## Step 2：逐链路确认角色

对每条高价值业务链路依次询问：

1. 哪些文件、方法或配置由你修改？
2. 哪些方案由你决定，哪些由 mentor 或团队给定？
3. 你亲自遇到过什么错误、返工或调试过程？
4. 你是否运行、测试或观察过结果？
5. 哪些部分只是读过，尚未动手？
6. 哪些部分希望用于简历，但当前掌握不够？

用户要求快速处理时，先让用户按链路选择角色：`主导 / 独立实现 / 参与实现 / 阅读理解 / 未接触`，再对候选 Bullet 追问细节。

Git 的职责边界：

- `git log/blame/show` 可以支持“谁在何时改了哪些代码、变更如何演进”；
- 当前代码、调用链和相关测试支持“系统最终做了什么、技术难点和边界是什么”；
- 用户口述、工单或评审记录支持“为什么做、谁做决策、真实结果是什么”；
- commit 大小、文件数、增删行数、提交次数和 ADR 数量不能支持“价值高、影响大、质量好”。

若 Git 与当前代码不一致，先按当前代码确定能力，再追踪相关提交确认个人边界；无法映射时标记 `CODE_INFERRED/HIGH`，不得因为提交很大而提高优先级。

## Step 3：生成贡献记录

每个贡献记录包含：

```json
{
  "id": "CONTRIBUTION-001",
  "chain_id": "CHAIN-001",
  "scope": "订单回调的幂等校验与异常补偿",
  "role": "参与实现",
  "source_type": "MENTOR_DIRECTED",
  "mastery_level": "L3",
  "code_locations": ["src/order/CallbackService.java"],
  "evidence_ids": ["EVIDENCE-012", "EVIDENCE-003"],
  "open_questions": [],
  "risk": "MEDIUM"
}
```

## Step 4：识别可包装内容与缺口

先对业务链路阶段传入的全部候选做价值排序，再创建核心声明。每个候选按下列六项各打 `0-2` 分，总分 `0-12`：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 业务/架构关键性 | 辅助细节 | 支撑局部流程 | 核心链路、公共平台或关键约束 |
| 工程深度 | 直接 CRUD/配置 | 多模块实现 | 并发、一致性、容错、复杂编排或演进 |
| 方案取舍 | 无决策 | 能解释一种选择 | 有约束、替代方案与代价 |
| 结果/验证 | 只有实现存在 | 静态范围或基础测试 | 业务结果、基准、故障验证或完整质量闭环 |
| 岗位相关性 | 弱相关 | 通用能力 | 命中目标岗位核心要求 |
| 面试可深挖性 | 只能复述 | 可解释流程 | 可讲问题、方案、失败边界和复盘 |

`9-12` 为强候选，`6-8` 为中候选，`0-5` 只作支撑材料。价值分不包含 Git 规模；角色、来源、掌握度和风险是独立准入门槛，不得用高价值掩盖个人归因不足。

将总分作为 `candidate_value_score` 写入贡献映射；这是后续简历排序与替换的唯一价值分。各维度原始分和一句评分理由同时保留，便于审计。简历阶段不得重新发明另一套权重；岗位相关性已包含在本分数中，角色、来源、掌握度和风险只作准入门槛，不与价值分相加。

要求 N 条简历要点时至少比较 `max(6, 2N)` 个候选。只从合格来源和角色中选择；同一功能的界面、接口、落库和文档默认合并为一项，除非各自存在独立技术决策和结果。角色、来源、掌握度或风险不合格的候选记录准入失败理由；已通过准入的高分候选若因与入选项主题重复而未入选，记录去重理由。岗位相关性已经计入 `candidate_value_score`，不得再次作为例外。

将每条候选内容分为：

- `READY`：可直接进入简历；
- `NEEDS_EVIDENCE`：缺数字、代码或用户确认；
- `NEEDS_TRAINING`：内容可用但掌握度不足；
- `NEEDS_BUILD`：需要完成增强、复现或二次开发；
- `BLOCKED`：说法自相矛盾或用户无法解释。

对 `NEEDS_TRAINING` 和 `NEEDS_BUILD` 生成具体输入，交给 `experience-lab.md`。

## Step 5：强制确认

🔴 CHECKPOINT · ROLE & SOURCE

展示以下表格后暂停：

| 候选经历 | 用户角色 | 来源 | 掌握度 | 风险 | 下一步 |
|---|---|---|---|---|---|
| {内容，含价值分与排名} | {角色} | {source_type} | {L0-L4} | {风险} | {入选/未入选理由或补强动作} |

用户可以修改角色、来源或希望保留的内容。用户已经授权全流程自动继续时，记录 `auto_confirmed=true`，继续执行，但不得省略表格和内部记录。

## contribution-map.md 模板

```markdown
# 个人贡献映射

## 用户模式
{模式及判定依据}

## 链路贡献
| 链路 | 项目实现 | 用户角色 | 来源 | 掌握度 | 风险 | 可否包装 |
|---|---|---|---|---|---|---|

## 候选声明
| 排名 | Claim ID | 类别 | 候选表述 | `candidate_value_score` | 评分理由 | 代码/测试证据 | Git 归因证据 | 当前状态 | 入选决定 |
|---:|---|---|---|---:|---|---|---|---|---|

## 待补空白
- {具体问题或增强任务}
```

## 失败模式

| 触发条件 | 一线修复 | 仍失败则 |
|---|---|---|
| 用户说“整个项目都是我做的”但项目很大 | 按核心链路逐条确认代码位置 | 将未确认部分标为 `CODE_INFERRED` |
| 用户完全不了解目标项目 | 选择 1 条最短核心链路进入复现 | 模式保持 `PROJECT_MIGRATION`，状态 `TRAINING_REQUIRED` |
| 用户只给简历没有代码 | 从 Bullet 反推需要的实现证据 | 用口述拷打建立临时贡献图 |
| 用户不愿回答角色问题 | 允许继续生成草稿 | 所有个人归属标为 `HIGH`，最终不可标 Ready |

## 不要做

- 不要把模块职责表当作个人角色表。
- 不要一次抛出十几个问题。
- 不要因用户没有实习而终止流程。
- 不要在贡献尚未确认时生成最终简历。
- 不要丢弃用户明确希望包装的高风险内容；应转入增强和拷打。
- 不要按提交时间、commit 大小或 diff 统计生成候选排名。
- 不要把同一提交里的前端、后端、文档机械拆成三条简历要点。
- 不要让较弱候选占位；存在更高分且准入合格的候选时必须替换。
